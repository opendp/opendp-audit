# `rust/src/transformations/make_stable_expr/expr_replace/mod.rs`

## Scope and assumptions

Review `make_expr_replace` and its literal helpers for the ordinary non-deprecated Polars `replace(old,new)` operation: output nullability, public-pattern validation, and data-dependent failure. Input expression is assumed already stable; `old` and `new` are public literals. Source is [OpenDP at `ef1a238634d6196b01a1a1e77d3d5ad2340e3094`](https://github.com/opendp/opendp/blob/ef1a238634d6196b01a1a1e77d3d5ad2340e3094/rust/src/transformations/make_stable_expr/expr_replace/mod.rs), with [OpenDP tests](https://github.com/opendp/opendp/blob/ef1a238634d6196b01a1a1e77d3d5ad2340e3094/rust/src/transformations/make_stable_expr/expr_replace/test.rs) and pinned [Polars replacement kernels](https://github.com/pola-rs/polars/blob/2a151c10fa76790711c2f75e6d012dd69c627ddd/crates/polars-ops/src/series/ops/replace.rs) (`py-1.36.1`). This review includes source inspection, independent finite-alphabet modeling, and a **compiled Polars 1.36.1 executor test**. Native OpenDP Rust constructor/execution behavior was reproduced against the pinned commit in [the dedicated GitHub Actions integration run](https://github.com/opendp/opendp-audit/actions/runs/45104162426). `replace_strict` and arbitrary optimizer rewrites are excluded.

## Analysis

The constructor requires literal `old` and `new` expressions, requires their lengths to match or permits one broadcast replacement, excludes categorical input, materializes dynamic list literals, and checks dtype compatibility. It calls `output_domain.column.set_dtype(dtype)` to discard stale value bounds, then computes nullable as `input_nullable || new_contains_null`, overriding this to **false** when `old_contains_null && !new_contains_null`.

For unique public replacement keys, this null-elimination rule agrees with pinned Polars: [`get_replacement_mask`](https://github.com/pola-rs/polars/blob/2a151c10fa76790711c2f75e6d012dd69c627ddd/crates/polars-ops/src/series/ops/replace.rs) matches NULL explicitly, `replace_by_single` fills null mask positions as true if `old` contains null, and `replace_by_multiple` uses a join with `nulls_equal: true`. An independently executed JavaScript model exhausted all unique `old` sequences of lengths 0–4 over `{NULL,-1,0,1}`, permitted `new` lists/broadcast values, both source nullability descriptors, and row values allowed by the descriptor. **8,133 mappings / 56,931 row cases:** zero null results declared non-nullable. This models the intended replacement semantics; it is not proof of backend execution, casting, or optimizer behavior.

**Public duplicate keys:** OpenDP validates only literal shape, length and type, not uniqueness. For `old=[1,1]`, `new=[10,20]`, input `Int32`, these OpenDP constructor checks pass. Pinned Polars [`replace`](https://github.com/pola-rs/polars/blob/2a151c10fa76790711c2f75e6d012dd69c627ddd/crates/polars-ops/src/series/ops/replace.rs) calls `validate_old`, which enforces `old.n_unique()? == old.len()` at **execution**. The [Polars expression DSL](https://github.com/pola-rs/polars/blob/2a151c10fa76790711c2f75e6d012dd69c627ddd/crates/polars-plan/src/dsl/mod.rs) only constructs the AST; it does not validate public key uniqueness. This is a predictable data-independent execution error from an accepted public parameter, not a demonstrated privacy leak. It is [tracked as reproduced issue #56](https://github.com/opendp/opendp-audit/issues/56): the cross-library constructor-to-collection failure is verified by native Rust and Polars tests.

**Compiled executor verification:** The actual `polars==1.36.1` Python wheel passed four integration tests in [GitHub Actions run #45104162426](https://github.com/opendp/opendp-audit/actions/runs/45104162426). `old=[1,1]` with `new=[10,20]` raised `InvalidOperationError` at `LazyFrame.collect()` both for data `[1,2]` and for data `[7,8]` containing no mapped keys. Distinct replacement keys returned `[10,20]`; `old=[NULL,1]` with `new=[0,10]` produced `[0,10,2]` for `[NULL,1,2]`. These are **native Polars executor tests**. The [companion Rust integration regression](https://github.com/opendp/opendp-audit/blob/0c8a70b192a444f1cb32d53bbbcecbd6c80a7c6e/tools/integration/polars_replace_open_dp.rs) independently compiled pinned OpenDP with Polars and passed all three tests in [the same workflow](https://github.com/opendp/opendp-audit/actions/runs/45104162426). The duplicate-key test constructs a stable transformation successfully for both `[1,2]` and `[7,8]`, then asserts that each `collect()` returns a Polars error containing `duplicates`. Positive tests confirm distinct-key replacement and null-key imputation; the latter also checks the OpenDP output descriptor is non-nullable. This is a **reproduced end-to-end API correctness failure**, not a data-dependent privacy leak.

**Experimental constructor-time remediation:** [Audit-only commit `c7c2f02`](https://github.com/opendp/opendp-audit/commit/c7c2f02034c9793d37a7fdea6eba95bd9c80da08) adds an [ephemeral patch script](https://github.com/opendp/opendp-audit/blob/c7c2f02034c9793d37a7fdea6eba95bd9c80da08/tools/integration/patch_polars_replace_duplicate_keys.py) and [native repaired tests](https://github.com/opendp/opendp-audit/blob/c7c2f02034c9793d37a7fdea6eba95bd9c80da08/tools/integration/polars_replace_repaired_open_dp.rs). The patch checks `LiteralValue::Series(old_series).n_unique()? == old_series.len()` **after literal materialization and datatype validation**, rejecting duplicate public keys at construction using the same Polars uniqueness method as the runtime. In [completed native CI run #45107956499](https://github.com/opendp/opendp-audit/actions/runs/45107956499), the original unpatched implementation **passed 3/3 tests**, demonstrating the existing defect; after applying the patch in a temporary checkout, the repaired implementation **passed 5/5 tests**: duplicated `Int32`, NULL and NaN keys rejected at construction, distinct/null-key mappings and scalar replacements accepted. The compiled Polars 1.36.1 control job also passed **4/4**. These are executed tests of an **experimental checkout-only patch**; upstream OpenDP remains unchanged. The prototype handles materialized `Series` key uniqueness only; newly reproduced Range dtype/bound and invalid UTF-8 cast errors remain unaddressed by that patch, and other casts/optimizer rewrites remain unchecked.

**Additional public-literal validation failures:** The pinned OpenDP constructor's `literal_len` treats a `RangeLiteralValue` as `high.saturating_sub(low)` and its `is_cast_fallible` only checks a coarse dtype predicate; it does not validate whether Polars can materialize that range. Pinned Polars `LiteralExpr` accepts range dtypes `Int32`, `Int64`, or `UInt32`, subject to bounds checks, and errors for unsupported dtype/bounds. Native [CI #45109555555](https://github.com/opendp/opendp-audit/actions/runs/45109555555) shows an `Expr::Literal(RangeLiteralValue { low: 0, high: 2, dtype: DataType::String })` is accepted by `make_stable_lazyframe` for String input but fails at `collect()` with `unsupported range datatype str`. A `UInt32` range `low=-1, high=2` likewise constructs and fails at collect with a range conversion error. An `Int32` range `[1,4)` successfully replaces rows keyed `1,2,3`, confirming this is not blanket rejection of Range.

**Public cast failure:** The same native run shows `old=Binary([0xff])`, `new=String(["replacement"])` and String input accepted by OpenDP construction, then failed at collection with `invalid utf8` on two input datasets. OpenDP's `is_cast_fallible` unconditionally treats casts *to* String as safe; Polars's runtime `strict_cast` fails for invalid UTF-8 public bytes. The compiled `polars==1.36.1` probe also reproduced the failure independently and tested three public key sets (`Float64` neighbors, signed integers and valid UTF-8 binary) for post-cast uniqueness without observing collisions. Those three sets are not exhaustive. [Native fixture](https://github.com/opendp/opendp-audit/blob/ccf70c8025b20c68fc55109106317218fcb44a86/tools/integration/polars_replace_range_open_dp.rs), [compiled probe](https://github.com/opendp/opendp-audit/blob/27267929bc30ea601c2c9d42cddbdbba5ac7c4a7/tools/integration/polars_replace_public_cast_probe.py).

These are **data-independent public-parameter correctness/availability failures**, not demonstrated privacy leakage. The [existing issue #56](https://github.com/opendp/opendp-audit/issues/56) tracks the shared missing constructor-time public-literal validation instead of creating separate repetitive issues. The previously tested CI-only Series uniqueness patch does **not** validate Range materializability or binary-to-String UTF-8 conversion.

The existing upstream tests cover scalar/list mappings, null imputation, null-valued replacements, and wrong dtype, but do not test duplicate public `old` keys. They were **inspected, not executed**. See [cross-file investigation](../../../../../../investigations/polars-replace-null-imputation-and-public-key-validation.md).
